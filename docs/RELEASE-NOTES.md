# Release notes

Write each GitHub release for someone who has not read the development conversation. Use simple headings and short paragraphs about changes they can see. Explain where to find new settings. Leave out empty sections.

Keep visible prose free of em dashes, en dashes, hyphens, semicolons and separator dots. Preserve working code, URLs, paths and asset names. Use paragraphs instead of bullet lists.

## Format

```markdown
## Added

New features and where to find them.

## Changed

Changes to defaults and navigation.

## Fixed

The problem and what works differently now.

## Assets

`Sunlith-v<version>.apk` is the Android app.

`Sunlith-companion-v<version>.zip` contains the computer connection tools and setup guide.

`SHA256SUMS.txt` contains checksums for checking the downloads.
```

The title is `Sunlith v<version>`. Keep test counts and verification details in TESTING.md. Include an upgrade step only when one is needed. Leave out routine installation instructions, marketing, generated change lists, contributor credits, screenshots and videos. Put Assets last, just above the downloads, and explain each file.

GitHub provides the download assets below the description. Keep setup instructions in the computer connection documentation.
