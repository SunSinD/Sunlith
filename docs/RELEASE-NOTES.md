# Release notes

Write each GitHub release for someone who has not read the development conversation. Use plain headings and concrete changes, grouped by feature. Include the behavior a user will notice and where to find new options. Omit empty categories.

## Format

```markdown
## Added

- New features and their useful settings.

## Changed

- Changes to defaults, navigation and existing behavior.

## Fixed

- Specific bugs and the resulting behavior.

## Validation

- Checks completed for this exact release, with relevant device or version limits.
```

The title is `Sunlith v<version>`. Keep the description neutral and specific. Do not add routine installation instructions, promises that existing data or pairing is preserved, marketing filler, generated change lists, contributor credits, screenshots or videos. Explain an upgrade step only when that release actually requires one. Link to detailed test results when they help; never reuse test counts from a different build.

GitHub provides the download assets below the description. Keep setup instructions in the computer connection documentation.
